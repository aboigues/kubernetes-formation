# Fiche TP9 — Gestion Multi-Nœud de Kubernetes

## Concepts clés
- **Taint** (posé sur un nœud) : repousse les pods, sauf ceux qui ont la **toleration** correspondante. Trois effets : `NoSchedule` (refuse les nouveaux pods), `PreferNoSchedule` (évite si possible), `NoExecute` (évacue même les pods déjà en place qui ne tolèrent pas).
- **Node affinity/anti-affinity** : contrainte sur les **labels d'un nœud**. **Pod affinity/anti-affinity** : contrainte sur la **présence d'autres pods**. Chacune existe en version `required` (dure, bloquante) ou `preferred` (souple, best-effort).
- **PodDisruptionBudget (PDB)** : `minAvailable`/`maxUnavailable` limite le nombre de pods qu'une opération **volontaire** (drain, upgrade) peut mettre hors service en même temps.
- Maintenance : `cordon` (marque le nœud non-schedulable, sans rien évacuer), `drain` (cordon + évacue proprement les pods existants, en respectant les PDB), `uncordon` (annule le cordon).
- **etcd** stocke tout l'état du cluster — sa sauvegarde/restauration est l'opération de disaster recovery la plus critique d'un cluster kubeadm.

## Commandes essentielles, expliquées

```bash
kubectl taint nodes worker1 dedicated=database:NoSchedule
```
Ajoute une répulsion sur `worker1` : tout nouveau pod sans toleration pour `dedicated=database` (avec l'effet `NoSchedule`) ne pourra plus y être planifié. Les pods déjà présents avant le taint ne sont **pas** affectés (contrairement à `NoExecute`).

```bash
kubectl taint nodes worker1 dedicated-
```
Le `-` final retire ce taint précis. Attention à l'ordre dans un tutoriel : si cette commande est exécutée juste avant un exemple censé démontrer l'effet du taint, l'exemple ne démontre plus rien puisque le taint n'existe déjà plus.

```bash
kubectl label nodes worker3 disktype=ssd
```
Pose un label arbitraire sur le nœud — utilisé ensuite par une `nodeAffinity` pour cibler spécifiquement ce nœud. Un label n'a aucun effet de répulsion par lui-même (contrairement à un taint) : il sert uniquement de critère de sélection positif.

```bash
kubectl cordon worker1
kubectl drain worker1 --ignore-daemonsets --delete-emptydir-data
kubectl uncordon worker1
```
`cordon` empêche tout nouveau pod d'arriver sur `worker1`, sans toucher aux pods déjà en place. `drain` va plus loin : il évince chaque pod existant (en respectant les PDB — un drain peut rester bloqué en attente si aucun budget de disruption ne le permet), en les laissant être recréés ailleurs par leur contrôleur. `--ignore-daemonsets` évite une erreur sur les pods DaemonSet, qui ne peuvent pas être "déplacés" par nature. `--delete-emptydir-data` accepte explicitement de perdre les données des volumes `emptyDir` du nœud (sinon `drain` refuse). `uncordon` réautorise le scheduling normal une fois la maintenance terminée.

```bash
kubectl get pdb
```
Liste les PodDisruptionBudget et leur état courant (`ALLOWED DISRUPTIONS` : combien de pods peuvent encore être évincés volontairement sans violer le budget). Une valeur à 0 bloque tout `drain` sur les pods concernés jusqu'à ce que la situation change (ex. un autre replica redevient `Ready`).

```bash
kubectl exec -n kube-system etcd-master1 -- etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt --cert=... --key=... \
  snapshot save /var/lib/etcd/snapshot.db
```
Se connecte à l'API etcd locale du pod statique `etcd-master1` (les certificats sont nécessaires car etcd chiffre son trafic même en local) et écrit un instantané complet de la base dans ce fichier — **à l'intérieur du pod**, pas encore récupéré localement.

```bash
kubectl cp kube-system/etcd-master1:/var/lib/etcd/snapshot.db ./etcd-snapshot.db
```
Rapatrie ce fichier sur la machine qui exécute `kubectl`. Sans cette étape, le snapshot reste piégé dans le pod et serait perdu si le nœud etcd est celui qui tombe en panne.

## ⚠️ Pièges fréquents (le plus contre-intuitif du dépôt)
- **Une toleration ne fait qu'AUTORISER** un pod à être planifié sur un nœud taint — elle ne l'y **force jamais**. Sans `nodeSelector`/`nodeAffinity` en plus, le scheduler peut tout aussi bien placer le pod sur un nœud sans aucun taint. "Je tolère" ≠ "je veux aller là" : c'est l'erreur la plus commune sur ce sujet.
- Un **PDB protège contre les disruptions volontaires** (drain, upgrade planifié) — il ne protège en rien contre un crash de nœud (disruption involontaire, hors de son contrôle). Il ne rend donc pas une application plus disponible en soi, seulement plus difficile à interrompre délibérément.
- Combiner une **nodeAffinity dure** (un seul nœud éligible) avec une **podAntiAffinity dure** (un pod par nœud maximum) limite mathématiquement le nombre de replicas réellement planifiables — au-delà, les pods excédentaires restent `Pending` indéfiniment, sans message d'erreur explicite au premier coup d'œil (`kubectl describe pod` le révèle dans les `Events`, avec un message du type "0/3 nodes are available").
- La restauration etcd exige d'arrêter proprement le pod statique (déplacer temporairement son manifeste hors de `/etc/kubernetes/manifests/`, laisser le kubelet le supprimer, remplacer les données, remettre le manifeste) — un simple `systemctl restart kubelet` ne force pas la recréation d'un pod statique déjà en cours d'exécution avec les mêmes specs.

## ✅ À retenir
Avant de supposer qu'un pod ira "logiquement" sur tel nœud grâce à une toleration, vérifier avec `kubectl get pod -o wide` — et si un placement précis est réellement requis, l'exprimer explicitement via affinité, pas en espérant que la toleration suffise à elle seule.
