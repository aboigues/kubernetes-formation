# Fiche TP10 — Projet de Synthèse : Application TaskFlow

## Concepts clés
Ce TP n'introduit pas de nouveau concept : il assemble tout ce qui précède dans une seule application multi-tiers (Frontend Nginx → Backend Flask → PostgreSQL + Redis + Prometheus + Grafana), avec HPA, initContainers, Services de plusieurs types, PVC, ConfigMaps/Secrets et RBAC pour le monitoring.

## Commandes essentielles
```bash
kubectl get all -n taskflow
kubectl get hpa -n taskflow -w
kubectl top pods -n taskflow
kubectl logs -n taskflow -l app=backend --tail=50
```

## ⚠️ Pièges fréquents
- Le principe du **moindre privilège** s'applique aussi au monitoring : un ServiceAccount Prometheus n'a besoin que de `nodes/metrics` pour scraper le kubelet — jamais de `nodes/proxy`, qui autorise un accès à **n'importe quel** endpoint du kubelet (risque d'escalade de privilèges, signalé par les scanners de sécurité sous KSV-0047).
- Une stack complète multiplie les points de defaillance possibles : en cas de blocage, isoler le tiers en cause (`kubectl get pods -n taskflow` pour repérer lequel n'est pas `Running`/`Ready`) avant de chercher plus loin.

## ✅ À retenir
Ce TP est un bon test de fin de parcours : si vous savez expliquer **chaque ligne** de chaque manifest — pourquoi ce `securityContext`, pourquoi cet `initContainer`, pourquoi ce verbe RBAC et pas un autre — vous maîtrisez le programme des TP1 à TP9.
