# Fiche TP10 — Projet de Synthèse : Application TaskFlow

## Concepts clés
Ce TP n'introduit pas de nouveau concept : il assemble tout ce qui précède dans une seule application multi-tiers (Frontend Nginx → Backend Flask → PostgreSQL + Redis + Prometheus + Grafana), avec HPA, initContainers, plusieurs types de Services, PVC, ConfigMaps/Secrets et RBAC pour le monitoring. La difficulté n'est plus dans un concept isolé mais dans leur **interaction** : un problème sur un tiers peut avoir sa cause racine sur un autre.

## Commandes essentielles, expliquées

```bash
kubectl get all -n taskflow
```
Liste en une fois Deployments, Services, Pods, ReplicaSets, HPA du namespace — un premier coup d'œil global avant de creuser un composant en particulier.

```bash
kubectl get hpa -n taskflow -w
```
`-w` (watch) montre en direct l'évolution du HPA (replicas actuels vs cible, utilisation CPU/mémoire mesurée) — utile pendant qu'un générateur de charge tourne, pour observer le scale-up puis le scale-down (avec le délai de ~5 minutes vu en TP4).

```bash
kubectl top pods -n taskflow
```
Nécessite Metrics Server (voir TP4). Sans lui installé, cette commande échoue avec une erreur explicite plutôt qu'un résultat vide — un bon indicateur pour vérifier que le prérequis est bien en place avant de chercher un autre problème.

```bash
kubectl logs -n taskflow -l app=backend --tail=50
```
Cible tous les pods backend (potentiellement plusieurs replicas) par label. Sur une stack multi-tiers, un problème apparaît souvent d'abord dans les logs du tiers **appelant** (ex. backend qui n'arrive pas à joindre la base) plutôt que dans celui qui est réellement en cause (base de données pas encore prête) — vérifier les deux avant de conclure.

## ⚠️ Pièges fréquents
- Le principe du **moindre privilège** s'applique aussi au monitoring : un ServiceAccount Prometheus n'a besoin que de `nodes/metrics` pour scraper le kubelet — jamais de `nodes/proxy`, qui autorise un accès à **n'importe quel** endpoint du kubelet (risque d'escalade de privilèges, signalé par les scanners de sécurité sous KSV-0047). Ce n'est pas un détail cosmétique : `nodes/proxy` donne un accès bien plus large que ce dont Prometheus a réellement besoin.
- Une stack complète multiplie les points de défaillance possibles : en cas de blocage, isoler le tiers en cause (`kubectl get pods -n taskflow` pour repérer lequel n'est pas `Running`/`Ready`) **avant** de lire des logs au hasard — remonter la chaîne de dépendances (frontend → backend → base) plutôt que de partir du composant le plus visible.
