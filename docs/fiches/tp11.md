# Fiche TP11 — Kubernetes Gateway API

## Concepts clés
- **Séparation des rôles**, contrairement à l'Ingress (une seule ressource, un seul rôle : le contrôleur gère infra + routage) :
  - `GatewayClass` : l'implémentation concrète (géré par le fournisseur d'infra, ex. nginx-gateway, Istio, Cilium)
  - `Gateway` : le point d'entrée réseau — IP/port/TLS (géré par la plateforme/infra)
  - `HTTPRoute` : les règles de routage — quel chemin va vers quel service (géré par chaque équipe applicative, potentiellement dans un autre namespace)
- Routage avancé : par chemin (`PathPrefix`, `Exact`), par en-tête HTTP, par poids (`weight`, pour du canary)
- Terminaison TLS au niveau du `Gateway`, pas de l'`HTTPRoute` — la gestion des certificats reste du ressort de l'infra, pas de l'équipe applicative

## Commandes essentielles, expliquées

```bash
kubectl get gatewayclass
```
Liste les implémentations Gateway API disponibles sur le cluster (installées par un contrôleur, ex. via Helm). Sans au moins une GatewayClass `Accepted`, aucun `Gateway` ne peut réellement fonctionner, même s'il se crée sans erreur apparente.

```bash
kubectl get gateway -A
```
Liste les Gateways de tous les namespaces avec leur statut (`Programmed: True` signifie que l'implémentation a bien pris en compte la configuration et alloué une adresse). `-A` est nécessaire car un Gateway est souvent créé dans un namespace d'infra séparé des équipes applicatives.

```bash
kubectl get httproute -A
```
Liste les règles de routage. Une HTTPRoute peut exister et apparaître ici sans être active : il faut vérifier qu'elle référence bien un Gateway existant et que ce Gateway l'autorise.

```bash
kubectl describe httproute <nom>
```
Montre, dans les conditions (`status.parents[].conditions`), si la route a été **acceptée** par le Gateway qu'elle référence. Une route rejetée (ex. namespace non autorisé par `allowedRoutes`) reste visible dans `kubectl get` mais n'a aucun effet réel — `describe` est indispensable pour distinguer "créée" de "active".

## ⚠️ Pièges fréquents
- Un `HTTPRoute` seul ne sert à rien : il doit référencer un `Gateway` existant via `parentRefs`, et ce Gateway doit explicitement l'accepter (`allowedRoutes.namespaces`). Sans ça, la route est créée avec succès (aucune erreur à l'`apply`) mais reste totalement inactive — toujours vérifier via `describe`, pas juste `get`.
- Les règles d'un `HTTPRoute` sont évaluées par **spécificité** (un match avec en-tête est plus spécifique qu'un match sans, un chemin exact plus qu'un préfixe), **pas simplement dans l'ordre de la liste** — deux règles qui semblent se chevaucher au premier regard ne sont pas forcément un bug si l'une est structurellement plus spécifique que l'autre (ex. même `PathPrefix` mais l'une avec un en-tête requis en plus).
- Migrer depuis un Ingress existant change le modèle mental, pas juste la syntaxe : ce n'est pas un remplacement 1-pour-1, c'est une redistribution des responsabilités entre équipe infra (GatewayClass, Gateway) et équipe applicative (HTTPRoute).

## ✅ À retenir
La Gateway API est le **successeur officiel** de l'Ingress (K8s 1.31+ pour la stabilité v1) : sur un nouveau projet, la préférer directement plutôt que de repartir sur des annotations Ingress spécifiques à un contrôleur, qui ne sont ni standardisées ni portables d'un contrôleur à l'autre.
