# Fiche TP11 — Kubernetes Gateway API

## Concepts clés
- **Séparation des rôles**, contrairement à l'Ingress (une seule ressource, un seul rôle) :
  - `GatewayClass` : l'implémentation (géré par le fournisseur d'infra)
  - `Gateway` : le point d'entrée réseau (géré par la plateforme/infra)
  - `HTTPRoute` : les règles de routage (géré par chaque équipe applicative)
- Routage avancé : par chemin (`PathPrefix`), par en-tête HTTP, par poids (canary)
- Terminaison TLS au niveau du `Gateway`

## Commandes essentielles
```bash
kubectl get gatewayclass
kubectl get gateway -A
kubectl get httproute -A
kubectl describe httproute <nom>
```

## ⚠️ Pièges fréquents
- Un `HTTPRoute` seul ne sert à rien : il doit référencer un `Gateway` existant via `parentRefs`, et ce Gateway doit explicitement l'accepter (`allowedRoutes.namespaces`). Sans ça, la route est créée mais jamais active.
- Les règles d'un `HTTPRoute` sont évaluées par **spécificité** (un match avec en-tête est plus spécifique qu'un match sans, un chemin exact plus qu'un préfixe), **pas simplement dans l'ordre de la liste** — deux règles qui semblent se chevaucher ne sont pas forcément un bug si l'une est structurellement plus spécifique que l'autre.
- Migrer depuis un Ingress existant change le modèle mental : ce n'est pas un remplacement 1-pour-1, c'est une redistribution des responsabilités entre infra et applicatif.

## ✅ À retenir
La Gateway API est le **successeur officiel** de l'Ingress (K8s 1.31+ pour la stabilité v1) : sur un nouveau projet, la préférer directement plutôt que de repartir sur des annotations Ingress spécifiques à un contrôleur.
