# Fiche TP4 — Monitoring et Gestion des Logs

## Concepts clés
- Les 3 piliers de l'observabilité : **métriques** (valeurs numériques dans le temps), **logs** (événements textuels), **traces** (parcours d'une requête à travers plusieurs services).
- **Metrics Server** collecte CPU/mémoire de chaque Pod/Node et les expose via l'API `metrics.k8s.io` — sans lui, `kubectl top` et le **HPA** n'ont aucune donnée.
- **HPA** (HorizontalPodAutoscaler) : ajuste `spec.replicas` d'un Deployment en fonction d'une métrique cible (par défaut CPU en %).
- **Probes** : `livenessProbe` (échec → le conteneur est **redémarré**), `readinessProbe` (échec → le Pod est **retiré du Service**, mais pas redémarré), `startupProbe` (désactive liveness/readiness tant qu'il n'a pas réussi une première fois — pour les démarrages lents).
- **Prometheus** scrape (récupère activement, en HTTP GET périodique) des endpoints `/metrics` ; **Grafana** interroge Prometheus pour afficher des dashboards. La découverte de cibles se fait par annotations (`prometheus.io/scrape: "true"`) lues via l'API Kubernetes.

## Commandes essentielles, expliquées

```bash
kubectl top nodes
kubectl top pods
```
Interroge l'API `metrics.k8s.io`, alimentée par Metrics Server — pas une mesure en temps réel exacte, mais un instantané rafraîchi toutes les ~15-60 secondes selon la config.

```bash
kubectl autoscale deployment web --min=2 --max=10 --cpu-percent=50
```
Crée un objet HPA qui référence le Deployment `web`. Le contrôleur HPA vérifie périodiquement (toutes les 15s par défaut) l'utilisation CPU moyenne de tous les Pods, et ajuste `replicas` pour viser 50% — au-dessus, il scale up ; en-dessous, il scale down (avec un délai, voir plus bas).

```bash
kubectl get hpa -w
```
`-w` (watch) garde la commande ouverte et affiche chaque changement d'état en continu, au lieu d'un instantané unique — utile pour observer le scaling en direct pendant qu'une charge est appliquée.

```bash
kubectl apply -f 07-prometheus-with-rules.yaml
kubectl rollout status deployment/prometheus -n monitoring
```
Si ce fichier modifie uniquement une ConfigMap (règles d'alerte) **sans toucher au pod template** du Deployment, `kubectl apply` ne déclenche aucun rollout et `rollout status` retourne instantanément "already rolled out" — ça ne prouve rien sur la prise en compte des nouvelles règles. Ici, le fichier modifie aussi le pod template (nouvel argument `--web.enable-lifecycle`, nouveau volume pour les règles), donc un vrai rollout a bien lieu, et attendre sa fin garantit que la vérification suivante lit les logs du nouveau pod, pas de l'ancien en cours de terminaison.

```bash
kubectl logs -n monitoring -l app=prometheus | grep -i "Loading configuration file"
```
Cherche dans les logs le message que Prometheus écrit **au démarrage** en lisant son fichier de config. Un message trouvé ne prouve la prise en compte de la nouvelle config que si on est sûr que le pod a bien redémarré depuis le changement — d'où l'utilité du `rollout status` juste avant.

## ⚠️ Pièges fréquents
- Le **HPA scale up** quasi instantanément mais **scale down** seulement après ~5 minutes (`stabilizationWindowSeconds` par défaut = 300s côté scale-down, 0s côté scale-up) — comportement volontaire anti-flapping (éviter d'osciller si la charge fluctue rapidement), pas une lenteur anormale du contrôleur.
- Modifier une **ConfigMap seule**, sans toucher au pod template, ne relance jamais rien automatiquement. `kubectl rollout status` n'a de sens que si le pod template a réellement changé — vérifier avec `kubectl rollout history deployment/<nom>` qu'une nouvelle révision existe bien avant de s'y fier comme preuve.
- Pour forcer la prise en compte d'une config changée sans modifier le pod template : soit `kubectl rollout restart deployment/<nom>` (force un nouveau rollout sans rien changer d'autre), soit un rechargement applicatif explicite (ex. `--web.enable-lifecycle` + appel HTTP `POST /-/reload` pour Prometheus).

## ✅ À retenir
`kubectl rollout status` répond à la question "le déploiement est-il fini ?", jamais à "la modification a-t-elle été prise en compte ?" — ce sont deux questions différentes qui ne coïncident que si le pod template a changé.
