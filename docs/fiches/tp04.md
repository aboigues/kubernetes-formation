# Fiche TP4 — Monitoring et Gestion des Logs

## Concepts clés
- Les 3 piliers de l'observabilité : métriques, logs, traces
- **Metrics Server** → **HPA** (HorizontalPodAutoscaler) : scaling automatique sur CPU/mémoire
- **Probes** : `livenessProbe` (redémarre si échec), `readinessProbe` (retire du load-balancing), `startupProbe` (tolère un démarrage lent)
- **Prometheus** (collecte) + **Grafana** (visualisation) ; découverte de cibles par annotations `prometheus.io/scrape`

## Commandes essentielles
```bash
kubectl top nodes / kubectl top pods
kubectl get hpa -w
kubectl autoscale deployment <nom> --min=2 --max=10 --cpu-percent=50
kubectl logs <pod> -f --tail=50
kubectl rollout status deployment/<nom>
```

## ⚠️ Pièges fréquents
- Le **HPA scale up** quasi instantanément mais **scale down** seulement après ~5 minutes (`stabilizationWindowSeconds` par défaut = 300s côté scale-down, 0s côté scale-up) — comportement volontaire anti-flapping, pas une lenteur anormale.
- Modifier une **ConfigMap seule** ne relance rien : si le pod template du Deployment ne change pas (même image, mêmes args, mêmes volumes), `kubectl apply` ne déclenche **aucun** rollout. `kubectl rollout status` retourne alors "already rolled out" instantanément — ça ne prouve rien sur la prise en compte de la nouvelle config.
- Pour forcer la prise en compte d'une config changée : soit modifier aussi le pod template (nouvel argument, nouveau volume…) pour provoquer un vrai rollout, soit `kubectl rollout restart deployment/<nom>`, soit un rechargement applicatif explicite (ex. `--web.enable-lifecycle` + `/-/reload` pour Prometheus).

## ✅ À retenir
`kubectl rollout status` n'a de sens que si le **pod template** a réellement changé. Avant de l'utiliser comme preuve qu'une modification est prise en compte, vérifier qu'elle a bien déclenché un nouveau ReplicaSet (`kubectl rollout history deployment/<nom>`).
