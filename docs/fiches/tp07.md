# Fiche TP7 — Migration Docker Compose vers Kubernetes

## Concepts clés
- Correspondance des concepts : un `service` Docker Compose devient un **Deployment + Service** Kubernetes ; `depends_on` devient un **initContainer** qui attend activement ; `volumes` devient un **PVC** ; `environment` devient une **ConfigMap** (non sensible) ou un **Secret** (sensible).
- **Kompose** : convertit automatiquement un `docker-compose.yml` en manifests Kubernetes — un point de départ à corriger et durcir, jamais une solution finale à appliquer telle quelle.
- Les **health checks** Kubernetes (`livenessProbe`/`readinessProbe`) sont plus riches que le `healthcheck` de Docker Compose : ils distinguent explicitement "redémarrer" (liveness) de "retirer temporairement du trafic" (readiness), deux réactions très différentes à un problème.

## Commandes essentielles, expliquées

```bash
kompose convert -f docker-compose.yml
```
Lit le fichier Compose et génère un fichier `.yaml` par service (Deployment + Service), plus un pour chaque volume déclaré. Kompose traduit ce qu'il peut traduire mécaniquement (ports, variables d'environnement, images) — il ne devine ni les health checks, ni les limites de ressources, ni la sécurité : ça reste à écrire à la main après conversion.

```bash
kubectl apply -f kubernetes-manifests/
```
Applique **tous** les fichiers YAML du dossier en une seule commande — l'ordre de création (namespace avant le reste, secret avant le pod qui le référence) n'est généralement pas garanti par `kubectl` lui-même ; c'est le comportement de retry des contrôleurs (un Pod qui échoue à monter un Secret inexistant repasse en attente puis réussit dès que le Secret apparaît) qui rend cette absence d'ordre supportable en pratique.

```bash
kubectl logs -l app=backend --tail=50
```
`-l` cible tous les pods portant ce label (utile si le Deployment a plusieurs replicas) ; `--tail=50` limite aux 50 dernières lignes de chaque pod, pour éviter un flot ingérable si les logs sont volumineux.

```bash
# Dans un initContainer, exemple d'attente active :
until nc -z database 5432; do sleep 2; done
```
`nc -z` (netcat, zero-I/O mode) teste juste si le port TCP 5432 accepte une connexion, sans envoyer de données — une boucle qui réessaie toutes les 2 secondes jusqu'à ce que la base de données soit réellement joignable. Le conteneur principal ne démarre qu'une fois cet initContainer terminé avec succès : c'est la vraie garantie que `depends_on` ne fournit pas dans Docker Compose.

## ⚠️ Pièges fréquents
- `depends_on` dans Docker Compose ne garantit **que l'ordre de démarrage** des conteneurs, jamais que le service dépendant est réellement prêt à répondre. En Kubernetes, il faut un initContainer qui attend activement (test TCP, appel HTTP santé) avant de laisser démarrer le conteneur principal — sinon le premier démarrage échoue de façon aléatoire selon la vitesse relative des deux services.
- La sécurité n'est **pas portée automatiquement** par la migration : Docker Compose ne force rien niveau `securityContext`, limites de ressources ou moindre privilège. Migrer un `docker-compose.yml` "tel quel" reproduit son absence de durcissement dans un environnement (Kubernetes) qui, lui, le permet — c'est le moment de l'ajouter, pas de le reporter.
- Les chemins relatifs de volumes changent de sens selon l'endroit où vit réellement le fichier `docker-compose.yml` sur disque : un chemin `./frontend` fonctionne différemment selon que le fichier est à la racine du projet ou dans un sous-dossier `docker-compose-app/` — toujours vérifier ce à quoi il pointe une fois le fichier déplacé, pas juste le recopier.

## ✅ À retenir
Une migration réussie n'est pas "faire pareil sur un autre orchestrateur" : c'est l'occasion d'ajouter ce que Docker Compose ne permettait pas nativement (health checks fiables, limites de ressources, moindre privilège) — pas juste de faire fonctionner Kompose une fois et de passer à autre chose.
