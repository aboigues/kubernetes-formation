# Fiche TP5 — Sécurité et RBAC

## Concepts clés
- **ServiceAccount** : identité d'un pod pour parler à l'API Kubernetes
- **Role/RoleBinding** (portée namespace) vs **ClusterRole/ClusterRoleBinding** (portée cluster entier)
- **SecurityContext** (pod + conteneur) : `runAsNonRoot`, `readOnlyRootFilesystem`, `capabilities: drop: [ALL]`, `seccompProfile`
- **NetworkPolicy** : isolation réseau (voir aussi fiche TP8)
- **Pod Security Standards** (labels de namespace `pod-security.kubernetes.io/enforce`) : remplace **PodSecurityPolicy**, supprimé de Kubernetes en v1.25

## Commandes essentielles
```bash
kubectl auth can-i list secrets --as=system:serviceaccount:<ns>:<sa>
kubectl get rolebinding,clusterrolebinding -A
kubectl describe sa <nom>
kubectl label namespace <ns> pod-security.kubernetes.io/enforce=restricted
```

## ⚠️ Pièges fréquents
- Un **ClusterRole** donne accès dans **tous** les namespaces du cluster, y compris `kube-system` — même en limitant à un seul verbe (`get`) et une seule ressource. Ce n'est pas un détail : c'est le sens même d'une ressource "cluster-scoped".
- **PodSecurityPolicy n'existe plus** depuis Kubernetes 1.25 (supprimé, pas juste déprécié) : tout manifest `apiVersion: policy/v1beta1, kind: PodSecurityPolicy` trouvé quelque part est obsolète et inapplicable.
- `pods/exec` et l'écriture sur les `services` sont des permissions à accorder avec parcimonie : elles contournent respectivement tout ce qu'un Deployment déclare, et peuvent détourner du trafic vers un autre pod.

## ✅ À retenir
Par défaut, préférer un **Role namespacé** à un **ClusterRole** — un ClusterRole ne se justifie que pour un composant qui doit réellement opérer sur tout le cluster (ex. Prometheus scrapant tous les nœuds).
