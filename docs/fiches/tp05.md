# Fiche TP5 — Sécurité et RBAC

## Concepts clés
- **ServiceAccount** : l'identité qu'un Pod présente à l'API Kubernetes (distincte de l'identité humaine d'un utilisateur `kubectl`). Chaque namespace a un ServiceAccount `default`, monté automatiquement dans chaque Pod sauf désactivation explicite.
- **Role/RoleBinding** (portée : un seul namespace) vs **ClusterRole/ClusterRoleBinding** (portée : tout le cluster). Un `Role` définit des permissions (verbes sur des ressources) ; un `RoleBinding` associe ce Role à un sujet (ServiceAccount, utilisateur, groupe).
- **SecurityContext** : `runAsNonRoot` (refuse de démarrer si l'image tourne en UID 0), `readOnlyRootFilesystem` (le système de fichiers racine du conteneur est immuable — tout ce qui a besoin d'écrire doit avoir un volume monté explicitement), `capabilities: drop: [ALL]` (retire tous les privilèges Linux fins par défaut, à ajouter un par un si nécessaire), `seccompProfile` (filtre les appels système autorisés).
- **Pod Security Standards** : trois niveaux (`privileged`, `baseline`, `restricted`) appliqués via un simple label sur le namespace — remplace **PodSecurityPolicy**, supprimé de Kubernetes en v1.25.

## Commandes essentielles, expliquées

```bash
kubectl create serviceaccount my-app-sa
```
Crée l'identité. À elle seule, elle n'a **aucune permission** — RBAC est "deny by default" : tout ce qui n'est pas explicitement autorisé par un Role/ClusterRole lié est refusé.

```bash
kubectl auth can-i list secrets --as=system:serviceaccount:default:my-app-sa
```
`--as` fait tourner la vérification **comme si** on était ce ServiceAccount, sans avoir besoin de générer un vrai jeton ni de lancer un Pod — un moyen rapide de tester une politique RBAC avant de la déployer pour de vrai.

```bash
kubectl auth can-i list secrets -n kube-system --as=system:serviceaccount:default:my-app-sa
```
Même vérification mais dans un **autre** namespace (`-n kube-system`). Si le ServiceAccount est lié à un **ClusterRole** via un **ClusterRoleBinding**, la réponse est `yes` ici aussi — un ClusterRoleBinding donne accès dans tous les namespaces, pas seulement celui du ServiceAccount.

```bash
kubectl label namespace mon-namespace pod-security.kubernetes.io/enforce=restricted
```
Active l'admission controller **PodSecurity** (intégré depuis 1.25) sur ce namespace en mode `restricted` : tout Pod qui ne respecte pas les règles du niveau `restricted` (root interdit, capabilities limitées, etc.) est **refusé à la création**, avant même d'exister — pas détecté après coup par un scanner.

```bash
kubectl describe sa my-app-sa
```
Montre les Secrets de type token associés (pour les anciennes versions de Kubernetes) ou confirme simplement l'existence du ServiceAccount — depuis 1.24+, les tokens sont générés à la demande (courte durée de vie) plutôt que stockés en Secret permanent.

## ⚠️ Pièges fréquents
- Un **ClusterRole** donne accès dans **tous** les namespaces du cluster, y compris `kube-system` — même en limitant à un seul verbe (`get`) et une seule ressource (`resourceNames: ["un-secret-precis"]`). Ce n'est pas un oubli de configuration à corriger : c'est le sens même d'une ressource "cluster-scoped". Si l'usage prévu est namespacé, c'est un `Role` + `RoleBinding` qu'il faut, pas un ClusterRole.
- **PodSecurityPolicy n'existe plus** depuis Kubernetes 1.25 (supprimé, pas juste déprécié) : tout manifest `apiVersion: policy/v1beta1, kind: PodSecurityPolicy` trouvé quelque part (documentation, ancien tutoriel) est obsolète et provoquera une erreur `no matches for kind` si on tente de l'appliquer.
- `pods/exec` et l'écriture sur les `services` sont des permissions à accorder avec parcimonie : `pods/exec` permet d'ouvrir un shell dans n'importe quel conteneur (contourne tout ce que le Deployment déclare : image scannée, variables, limites), et l'écriture sur `services` permet de détourner du trafic vers un autre Pod en changeant un `selector`.

## ✅ À retenir
Par défaut, préférer un **Role namespacé** à un **ClusterRole** — un ClusterRole ne se justifie que pour un composant qui doit réellement opérer sur tout le cluster (ex. Prometheus qui scrape les métriques de tous les nœuds).
