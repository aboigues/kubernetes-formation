# Fiche TP1 — Premier déploiement Kubernetes

## Concepts clés
- **Pod** : plus petite unité déployable. Un ou plusieurs conteneurs qui partagent le même namespace réseau (une seule IP pour le Pod) et peuvent partager des volumes. Un Pod n'est jamais "réparé" — s'il meurt, un nouveau est créé à sa place avec un nouveau nom et une nouvelle IP.
- **Deployment** : ne gère pas les Pods directement. Il crée et pilote un **ReplicaSet**, qui lui-même crée et surveille en continu N Pods identiques. Le Deployment ajoute par-dessus la logique de rolling update/rollback (il garde plusieurs ReplicaSets en historique).
- **Service** : une IP stable + un nom DNS qui pointent vers un ensemble de Pods sélectionnés par labels. Trois types principaux : `ClusterIP` (accessible uniquement depuis l'intérieur du cluster), `NodePort` (ouvre le même port sur chaque nœud), `LoadBalancer` (demande une IP publique au cloud provider — sans effet sur minikube sauf `minikube tunnel`).
- **Rolling update** : remplacement progressif des anciens Pods par les nouveaux, contrôlé par `maxSurge` (combien de Pods en plus temporairement) et `maxUnavailable` (combien de Pods en moins temporairement) — objectif : zéro interruption de service.

## Commandes essentielles, expliquées

```bash
kubectl create deployment web --image=nginx:alpine --replicas=3
```
Crée un Deployment nommé `web`. Ce Deployment crée un ReplicaSet, qui crée 3 Pods avec le label `app=web` (label ajouté automatiquement, dérivé du nom du Deployment). C'est le ReplicaSet — pas le Deployment — qui vérifie en continu qu'il y a bien 3 Pods `Running` et en recrée si l'un meurt.

```bash
kubectl get pods -o wide
```
`-o wide` ajoute l'IP du Pod et le nœud qui l'héberge à la sortie standard. Utile pour vérifier la répartition entre nœuds ou pour tester une connectivité directe (`curl <IP-du-pod>`).

```bash
kubectl describe pod <pod>
```
Affiche la configuration complète du Pod **et**, en bas de la sortie, la section `Events` — c'est presque toujours là qu'est l'information utile pour comprendre pourquoi un Pod ne démarre pas (image introuvable, ressources insuffisantes, volume qui ne se monte pas, etc.).

```bash
kubectl logs <pod> -f
```
Sans `-f`, affiche un instantané des logs déjà écrits puis rend la main. Avec `-f` (follow), le flux reste ouvert et affiche les nouvelles lignes en continu, comme `tail -f`.

```bash
kubectl exec -it <pod> -- sh
```
`-i` (interactive) garde stdin ouvert vers le conteneur ; `-t` alloue un pseudo-terminal. Les deux ensemble donnent un vrai shell interactif — avec un seul des deux, la commande s'exécute mais l'interaction est cassée (pas d'invite, ou entrée bloquée).

```bash
kubectl expose deployment web --type=NodePort --port=80
```
Crée un Service dont le `selector` reprend automatiquement les labels du Deployment ciblé. `--port=80` est le port exposé par le Service ; sans `--target-port`, Kubernetes suppose que le port du conteneur est le même. `NodePort` réserve en plus un port aléatoire entre 30000 et 32767 sur **chaque nœud** du cluster, qui redirige vers ce Service.

```bash
kubectl scale deployment web --replicas=5
```
Modifie uniquement le champ `spec.replicas` de l'objet Deployment. C'est le ReplicaSet qui, en observant cet écart, crée ou détruit des Pods pour converger vers le nombre demandé — l'opération elle-même est asynchrone.

```bash
kubectl set image deployment/web nginx=nginx:1.27-alpine
```
Modifie le pod template du Deployment (l'image du conteneur nommé `nginx`). Comme le pod template change, un **nouveau ReplicaSet** est créé et un rolling update démarre : l'ancien ReplicaSet décroît pendant que le nouveau croît, selon la stratégie `RollingUpdate` par défaut.

```bash
kubectl rollout status deployment/web
```
Ne déclenche rien : observe et bloque jusqu'à ce que le rollout en cours se termine (ou échoue au bout du timeout). N'a de sens que juste après une commande qui a réellement changé le pod template — sinon il retourne immédiatement "already rolled out" sans rien garantir sur le contenu réellement actif.

```bash
kubectl rollout undo deployment/web
```
Revient au ReplicaSet précédent, conservé dans l'historique des révisions (`kubectl rollout history deployment/web`). Ce n'est pas un retour en arrière instantané : c'est un rolling update inversé, avec les mêmes garanties de disponibilité progressive que la mise à jour d'origine.

## ⚠️ Pièges fréquents
- **Image non pinnée** (`nginx:latest`) : le contenu de `latest` change dans le temps, un déploiement reproductible aujourd'hui peut casser demain. Toujours épingler une version.
- **Secret en clair dans un manifest** (`value: "motdepasse"`) : utiliser un `Secret` + `secretKeyRef`, dès le premier exercice. C'est une règle facile à énoncer et étonnamment facile à ne pas appliquer soi-même : un audit dédié à la sécurité de ce dépôt en a quand même trouvé neuf occurrences oubliées ailleurs, dont deux dans des fichiers déjà corrigés pour d'autres raisons juste avant. Un réflexe simple pour se relire : `grep -rn 'value:.*PASSWORD' -B1` sur ses propres manifests avant de les considérer finis.
- **`kubectl create deployment <nom>`** étiquette automatiquement les pods `app=<nom>` : un Service qui sélectionne un autre label (ex. `app: database` pour un deployment nommé `db`) ne matchera **aucun** pod.

## ✅ À retenir
Avant de chercher plus loin sur un problème de connectivité, toujours vérifier `kubectl get endpoints <service>` — vide, c'est presque toujours un mismatch de labels entre le `selector` du Service et les `labels` du Pod, pas un problème réseau plus profond.
