# Fiche TP2 — Maîtriser les Manifests Kubernetes

## Concepts clés
- Anatomie d'un manifest : `apiVersion`, `kind`, `metadata`, `spec`
- **ConfigMap** (config non sensible) vs **Secret** (données sensibles, encodées base64 — pas chiffrées par défaut)
- **Labels & Selectors** : `matchLabels` (égalité stricte, ET implicite) vs `matchExpressions` (`In`, `NotIn`, `Exists`, `DoesNotExist`)
- **Namespaces** : isolation logique des ressources
- **Sidecar containers natifs** (K8s 1.29+) : `initContainers` avec `restartPolicy: Always` — démarre avant le conteneur principal et reste actif à ses côtés

## Commandes essentielles
```bash
kubectl apply -f fichier.yaml
kubectl apply -f fichier.yaml --dry-run=server   # valider sans appliquer
kubectl diff -f fichier.yaml                     # voir ce qui changerait
kubectl explain pod.spec.containers               # doc intégrée d'un champ
kubectl create configmap <nom> --from-literal=key=value
kubectl create secret generic <nom> --from-literal=password=xxx
kubectl get pods -l app=demo
kubectl label pod <pod> env=prod --overwrite
```

## ⚠️ Pièges fréquents
- Modifier une **ConfigMap montée en volume** ne redémarre PAS automatiquement le pod qui la lit — le contenu du fichier finit par se mettre à jour côté kubelet (sync périodique), mais l'application doit elle-même recharger sa config, ou il faut changer le pod template pour déclencher un vrai rollout (voir fiche TP4).
- `matchLabels` exige une correspondance exacte sur **tous** les labels listés — un seul label en trop ou en moins et plus rien ne matche.
- Un Secret n'est **pas chiffré**, juste encodé en base64 : ne pas le committer dans Git, ne pas le considérer comme sécurisé par défaut (voir TP5 pour le chiffrement au repos et les bonnes pratiques RBAC associées).

## ✅ À retenir
`kubectl apply --dry-run=server` avant chaque application réelle — il valide contre l'API server (schémas, admission controllers) sans rien créer, contrairement à `--dry-run=client` qui ne fait qu'une validation syntaxique locale.
