# Fiche TP2 — Maîtriser les Manifests Kubernetes

## Concepts clés
- Anatomie d'un manifest : `apiVersion` (groupe + version de l'API), `kind` (type de ressource), `metadata` (nom, namespace, labels), `spec` (état désiré — le seul champ qui varie vraiment d'un kind à l'autre)
- **ConfigMap** (config non sensible, en clair) vs **Secret** (même mécanisme technique, mais encodé en base64 et traité différemment par l'API — jamais chiffré par défaut)
- **Labels & Selectors** : `matchLabels` (égalité stricte sur chaque clé listée, ET implicite entre elles) vs `matchExpressions` (`In`, `NotIn`, `Exists`, `DoesNotExist` — plus expressif)
- **Namespaces** : isolation logique, pas réseau (une NetworkPolicy est nécessaire pour isoler réellement le trafic, voir TP8)
- **Sidecar containers natifs** (K8s 1.29+) : un `initContainer` avec `restartPolicy: Always` démarre avant le conteneur principal comme un init classique, mais **reste actif** à ses côtés au lieu de se terminer — Kubernetes attend que son propre `readinessProbe` passe avant de considérer le Pod prêt

## Commandes essentielles, expliquées

```bash
kubectl apply -f fichier.yaml
```
Calcule un diff entre l'état actuellement stocké dans etcd (via une annotation qui garde la dernière config appliquée) et le contenu du fichier, puis n'envoie que le patch nécessaire. Contrairement à `kubectl create`, `apply` est idempotent : le rejouer sans changement ne fait rien.

```bash
kubectl apply -f fichier.yaml --dry-run=server
```
Envoie la requête jusqu'à l'API server, qui la valide complètement (schéma, admission controllers, webhooks) **sans la persister**. Plus fiable que `--dry-run=client`, qui ne fait qu'une validation syntaxique locale sans jamais contacter le cluster — donc incapable de détecter, par exemple, qu'une ressource référencée (ConfigMap, ServiceAccount) n'existe pas.

```bash
kubectl diff -f fichier.yaml
```
Montre précisément ce qui changerait si le fichier était appliqué, sans l'appliquer — utile avant de modifier une ressource déjà en place pour éviter les surprises.

```bash
kubectl explain pod.spec.containers.securityContext
```
Interroge le schéma OpenAPI exposé par l'API server elle-même (pas une doc statique) : donne la documentation exacte des champs disponibles pour la version de Kubernetes réellement installée, y compris les champs récents ou spécifiques à un CRD.

```bash
kubectl create configmap app-config --from-literal=LOG_LEVEL=info
```
Crée une ConfigMap avec une seule clé (`LOG_LEVEL`) et sa valeur (`info`). `--from-file=<chemin>` fait la même chose mais utilise le nom du fichier comme clé et son contenu entier comme valeur — pratique pour charger un fichier de config complet (ex. `nginx.conf`) tel quel.

```bash
kubectl create secret generic db-credentials --from-literal=password=xxx
```
Même mécanisme qu'une ConfigMap, mais l'API stocke la valeur encodée en base64 (`kubectl get secret db-credentials -o yaml` le montre) et Kubernetes ne l'affiche jamais en clair dans `kubectl get`/`describe`. Base64 n'est **pas du chiffrement** — n'importe qui avec accès en lecture au Secret peut le décoder (`base64 -d`).

```bash
kubectl get pods -l app=demo
```
`-l` (label selector) filtre côté serveur, pas côté client — sur un cluster avec des milliers de pods, c'est nettement plus efficace qu'un `grep` après coup.

```bash
kubectl label pod <pod> env=prod --overwrite
```
Ajoute ou modifie un label sur une ressource déjà créée, sans avoir à ré-appliquer tout le manifest. `--overwrite` est obligatoire si le label existe déjà avec une autre valeur — sans lui, la commande refuse d'écraser silencieusement.

## ⚠️ Pièges fréquents
- Modifier une **ConfigMap montée en volume** ne redémarre PAS automatiquement le pod qui la lit. Le kubelet finit par mettre à jour le fichier monté (sync périodique, jusqu'à ~1 minute de délai), mais l'application doit elle-même surveiller ce fichier et recharger sa config — ou il faut changer le pod template pour déclencher un vrai rollout (voir fiche TP4 pour un exemple concret et vérifié).
- `matchLabels` exige une correspondance exacte sur **tous** les labels listés (ET logique) : un seul label en trop côté Pod n'empêche rien, mais un seul label **manquant ou différent** exclut le Pod du selector.
- Un Secret n'est **pas chiffré**, juste encodé : ne jamais le committer dans Git, ne jamais le considérer comme sécurisé par défaut au repos (voir TP5 pour le chiffrement etcd et les bonnes pratiques RBAC associées).

## ✅ À retenir
`kubectl apply --dry-run=server` avant chaque application réelle sur un manifest qui référence d'autres ressources (ConfigMap, Secret, ServiceAccount) — c'est le seul mode qui détecte une référence cassée avant qu'elle ne cause un `CrashLoopBackOff` ou un Pod bloqué en `ContainerCreating`.
