# Fiche TP6 — Mise en Production et CI/CD

## Concepts clés
- **Helm** : gère un ensemble de manifests comme un seul package versionné (chart). `values.yaml` paramètre le chart ; une **release** est une instance installée d'un chart avec des valeurs données.
- **Ingress** (une ressource, un rôle : le contrôleur gère infra + routage) vs **Gateway API** (successeur officiel K8s 1.31+, sépare infra et routage — détaillé en TP11).
- Stratégies de déploiement : **Rolling Update** (par défaut, progressif), **Blue-Green** (deux environnements complets, bascule instantanée du trafic), **Canary** (petite fraction du trafic vers la nouvelle version avant généralisation), **A/B testing** (routage basé sur des critères métier, pas juste un pourcentage).
- **GitOps avec ArgoCD** : un contrôleur dans le cluster compare en continu l'état réellement déployé à l'état déclaré dans un dépôt Git, et corrige tout écart — le cluster ne fait que "suivre" Git, jamais l'inverse.
- **Kustomize** : compose des manifests par superposition de patches (`base` + `overlays`), sans templating ni langage à apprendre — contrairement à Helm.

## Commandes essentielles, expliquées

```bash
helm install my-app ./01-helm/my-app --namespace production --create-namespace
```
Installe le chart situé dans ce dossier local sous le nom de release `my-app`. `--create-namespace` évite une erreur si le namespace `production` n'existe pas encore. Helm crée les objets Kubernetes définis par le chart, en substituant les `{{ .Values.xxx }}` par les valeurs de `values.yaml` (ou celles données en ligne de commande).

```bash
helm upgrade --install my-app ./01-helm/my-app --set image.tag=abc123 --wait --timeout 5m
```
`upgrade --install` fait un install si la release n'existe pas encore, sinon un upgrade — pratique dans un pipeline CI qui ne sait pas toujours si c'est le premier déploiement. `--set` surcharge une valeur précise sans toucher au fichier `values.yaml`. `--wait` bloque jusqu'à ce que tous les objets soient `Ready` (pas juste créés), `--timeout` limite cette attente.

```bash
helm template ./01-helm/my-app
```
Génère et affiche le YAML final **sans** contacter le cluster ni rien installer — l'équivalent de `kubectl apply --dry-run=client` mais pour un chart Helm entier. Le réflexe à avoir avant tout `install`/`upgrade` réel.

```bash
helm rollback my-app 2
```
Revient à la révision n°2 de cette release (visible via `helm history my-app`). Helm réapplique l'état complet de cette révision, comme un `kubectl rollout undo` mais au niveau du chart entier plutôt que d'un seul Deployment.

```bash
DEPLOYMENT_NAME=$(kubectl get deployments -n production -l app.kubernetes.io/instance=my-app -o jsonpath='{.items[0].metadata.name}')
kubectl rollout status deployment/$DEPLOYMENT_NAME -n production
```
Helm nomme les ressources `<release>-<chart>` (ex. `my-app-my-app`), pas juste `<release>` — un script qui suppose l'inverse cible un objet qui n'existe pas. La bonne pratique est de retrouver le nom réel via le label standard `app.kubernetes.io/instance=<release>`, posé automatiquement par les charts qui suivent les conventions Helm.

```bash
kubectl apply -k overlays/production/
```
`-k` déclenche Kustomize : lit `kustomization.yaml` dans ce dossier, applique la `base` référencée puis les patches de cet overlay (ex. changer le nombre de replicas, ajouter un namespace), et envoie le résultat final à l'API — un seul YAML de sortie, pas de fusion faite côté cluster.

```bash
argocd app sync my-app
```
Force une synchronisation immédiate entre l'état Git et le cluster (normalement automatique, à intervalle régulier). Toute modification faite directement sur le cluster (`kubectl edit`) sans passer par un commit Git sera écrasée au prochain sync — c'est le comportement voulu de GitOps, pas un bug.

## ⚠️ Pièges fréquents
- Helm nomme les ressources `<release>-<chart>`, **pas** juste `<release>` — toujours vérifier le nom réel via `kubectl get all -l app.kubernetes.io/instance=<release>` plutôt que de le deviner.
- Dans un pipeline CI/CD, ne jamais utiliser d'image non épinglée (`:latest`) : un build reproductible aujourd'hui doit le rester demain, sinon un rollback vers une "ancienne version" peut en réalité retélécharger une image différente de celle qui tournait à l'époque.
- ArgoCD ne fait que refléter Git : toute divergence manuelle sur le cluster est corrigée (écrasée) au prochain sync, jamais propagée vers Git dans l'autre sens.

## ✅ À retenir
`helm template` avant `helm install`/`upgrade` : ça prévisualise exactement le YAML qui sera appliqué, sans toucher au cluster — le réflexe équivalent au `kubectl apply --dry-run=server` du TP2, appliqué à l'échelle d'un chart entier.
