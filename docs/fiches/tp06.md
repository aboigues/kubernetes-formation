# Fiche TP6 — Mise en Production et CI/CD

## Concepts clés
- **Helm** : charts, `values.yaml`, releases (`helm install/upgrade/rollback`)
- **Ingress** vs **Gateway API** (successeur officiel, K8s 1.31+ — voir aussi TP8 §7 et TP11 en détail)
- Stratégies de déploiement : Rolling Update, Blue-Green, Canary, A/B testing
- **GitOps** avec ArgoCD : le cluster converge vers l'état déclaré dans Git
- **Kustomize** : base + overlays par environnement (dev/staging/prod), sans templating

## Commandes essentielles
```bash
helm install <release> <chart> --namespace <ns> --create-namespace
helm upgrade --install <release> <chart> --set image.tag=<sha>
helm template <chart>          # prévisualiser le YAML généré
helm rollback <release> <n>
kubectl apply -k overlays/prod/
argocd app sync <app>
```

## ⚠️ Pièges fréquents
- Helm nomme les ressources `<release>-<chart>`, **pas** juste `<release>` — un script qui suppose `kubectl rollout status deployment/<release>` peut cibler un objet qui n'existe pas. Utiliser un sélecteur par label (`app.kubernetes.io/instance=<release>`) pour retrouver le nom réel.
- Dans un pipeline CI/CD, ne jamais utiliser d'image non épinglée (`:latest`) : un build reproductible aujourd'hui doit le rester demain.
- ArgoCD ne fait que **refléter** l'état de Git : un `kubectl edit` direct sur le cluster sera écrasé au prochain sync — toute modification doit passer par un commit.

## ✅ À retenir
`helm template` avant `helm install`/`upgrade` : ça prévisualise exactement le YAML qui sera appliqué, sans toucher au cluster — le réflexe équivalent au `kubectl apply --dry-run=server` du TP2.
