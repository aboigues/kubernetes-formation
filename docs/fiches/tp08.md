# Fiche TP8 — Réseau Kubernetes : Services, DNS et Connectivité

## Concepts clés
- Types de Service : `ClusterIP`, `NodePort`, `LoadBalancer`, `ExternalName`, **Headless** (`clusterIP: None`)
- DNS interne (CoreDNS) : `<service>.<namespace>.svc.cluster.local`
- **NetworkPolicy** : `podSelector`, règles `ingress`/`egress` séparées
- Aperçu Gateway API (K8s 1.31+) — approfondi en TP11

## Commandes essentielles
```bash
kubectl get endpoints <service>
kubectl run tmp --image=busybox --rm -it -- nslookup <service>
kubectl exec -it <pod> -- wget -qO- http://<service>
kubectl describe networkpolicy <nom>
```

## ⚠️ Pièges fréquents
- **Premier réflexe de debug réseau** : `kubectl get endpoints <service>`. Vide = les labels du `selector` du Service ne matchent aucun pod (mismatch fréquent, ex. `kubectl create deployment db` étiquette les pods `app=db`, pas `app=database`).
- Une NetworkPolicy qui sélectionne un pod le bascule en **deny par défaut sur la seule direction qu'elle référence** (`policyTypes: [Ingress]` ne touche pas à l'egress, et inversement) — il faut deux policies pour bloquer les deux sens.
- Le **DNS (port 53 UDP/TCP)** est presque toujours oublié dans une politique egress "deny-all" — sans règle explicite l'autorisant, plus aucune résolution de nom ne fonctionne dans le pod concerné, y compris pour joindre des services internes par leur nom.

## ✅ À retenir
Diagnostiquer un problème réseau dans l'ordre : `endpoints` (le Service voit-il des pods ?) → `nslookup` (la résolution DNS fonctionne-t-elle ?) → `NetworkPolicy` (une règle bloque-t-elle le trafic ?). Sauter une étape fait perdre du temps sur les deux suivantes.
