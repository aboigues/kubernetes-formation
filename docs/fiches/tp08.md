# Fiche TP8 — Réseau Kubernetes : Services, DNS et Connectivité

## Concepts clés
- Types de Service : `ClusterIP` (IP interne, par défaut), `NodePort` (+ port ouvert sur chaque nœud), `LoadBalancer` (+ IP publique cloud), `ExternalName` (simple alias DNS, aucun contrôle réseau), **Headless** (`clusterIP: None` — résout vers les IPs de tous les pods directement, sans passer par une IP de service virtuelle).
- **DNS interne (CoreDNS)** : chaque Service obtient un nom `<service>.<namespace>.svc.cluster.local`, résolu automatiquement depuis n'importe quel Pod du cluster.
- **NetworkPolicy** : `podSelector` choisit les pods concernés ; des règles `ingress` (trafic entrant) et `egress` (trafic sortant) séparées, chacune activée uniquement si elle est explicitement listée dans `policyTypes`.
- Aperçu de la Gateway API (K8s 1.31+, approfondie en TP11) : sépare l'infrastructure réseau (Gateway) du routage applicatif (HTTPRoute), contrairement à l'Ingress qui mélange les deux.

## Commandes essentielles, expliquées

```bash
kubectl get endpoints <service>
```
Montre les IPs de Pods que le Service a effectivement sélectionnées **en ce moment** (calculé automatiquement par le contrôleur Endpoints à partir du `selector`). Une liste vide veut dire qu'aucun Pod ne porte les labels attendus — c'est la première chose à vérifier sur tout problème de connectivité, avant de soupçonner un problème réseau plus profond.

```bash
kubectl run tmp --image=busybox --rm -it -- nslookup <service>
```
Lance un Pod jetable (`--rm` le supprime en sortie), interactif (`-it`), qui interroge CoreDNS pour résoudre le nom du Service. Si la résolution échoue, le problème est DNS (CoreDNS down, NetworkPolicy bloquant le port 53) ; si elle réussit mais que la connexion échoue ensuite, le problème est ailleurs (endpoints vides, NetworkPolicy bloquant le trafic applicatif).

```bash
kubectl exec -it <pod> -- wget -qO- http://<service>
```
Teste la connectivité applicative réelle depuis l'intérieur d'un pod déjà existant (contrairement à `nslookup` qui ne teste que le DNS). `-qO-` (quiet, output vers stdout) affiche directement la réponse HTTP sans bruit ni fichier temporaire.

```bash
kubectl describe networkpolicy <nom>
```
Affiche les règles interprétées (pas juste le YAML brut) : quels pods sont sélectionnés, quelles règles ingress/egress s'appliquent. Utile pour vérifier que le `podSelector` cible vraiment les pods voulus avant de chercher un bug ailleurs.

```bash
kubectl create deployment database --image=mysql:8 --replicas=3
kubectl set env deployment/database MYSQL_ROOT_PASSWORD=secret
kubectl rollout status deployment/database --timeout=120s
```
`kubectl create deployment database` étiquette les pods `app=database` — le nom du Deployment compte, un Service qui sélectionne `app: database` ne fonctionnerait pas avec un Deployment nommé `db`. L'image MySQL officielle refuse de démarrer sans mot de passe root : les pods partent en `CrashLoopBackOff` jusqu'à ce que `kubectl set env` déclenche un nouveau rollout avec la variable définie. `rollout status` attend la fin de ce rollout avant de continuer, pour éviter un test DNS sur des pods pas encore prêts.

## ⚠️ Pièges fréquents
- **Premier réflexe de debug réseau** : `kubectl get endpoints <service>`. Vide = les labels du `selector` du Service ne matchent aucun pod (mismatch fréquent, ex. `kubectl create deployment db` étiquette les pods `app=db`, pas `app=database`).
- Une NetworkPolicy qui sélectionne un pod le bascule en **deny par défaut sur la seule direction listée dans `policyTypes`** (`[Ingress]` ne touche pas à l'egress, et inversement) — il faut deux policies (une par direction) pour bloquer les deux sens du trafic.
- Le **DNS (port 53 UDP/TCP)** est presque toujours oublié dans une politique egress "deny-all" — sans règle explicite l'autorisant vers CoreDNS, plus aucune résolution de nom ne fonctionne dans le pod concerné, y compris pour joindre des services internes par leur nom (l'IP directe fonctionnerait encore, le nom non).

## ✅ À retenir
Diagnostiquer un problème réseau dans l'ordre : `endpoints` (le Service voit-il des pods ?) → `nslookup` (la résolution DNS fonctionne-t-elle ?) → `NetworkPolicy` (une règle bloque-t-elle le trafic applicatif ?). Sauter une étape fait perdre du temps sur les deux suivantes, qui supposent implicitement que la précédente est déjà écartée.
