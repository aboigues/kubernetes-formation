# Fiche TP3 — Persistance des données

## Concepts clés
- **emptyDir** (éphémère, lié au pod) vs **hostPath** (dev uniquement) vs **PV/PVC** (persistant, découplé du pod)
- **PersistentVolume (PV)** : la ressource de stockage ; **PersistentVolumeClaim (PVC)** : la demande d'un pod
- **StorageClass** : provisionnement (manuel `no-provisioner` ou dynamique) + `volumeBindingMode`
- `accessModes` (ReadWriteOnce, ReadOnlyMany, ReadWriteMany), `reclaimPolicy` (Retain/Delete)

## Commandes essentielles
```bash
kubectl get pv,pvc
kubectl describe pvc <nom>
kubectl get storageclass
minikube ssh "sudo mkdir -p /mnt/data"   # pour un PV hostPath sous minikube
```

## ⚠️ Pièges fréquents (les plus importants du dépôt)
- **`volumeBindingMode: WaitForFirstConsumer`** : le PVC reste `Pending` tant qu'aucun **pod** ne le consomme — ce n'est **pas un bug**, c'est voulu : le binding attend de savoir sur quel nœud le pod sera planifié avant de choisir/lier un volume. Le binding a lieu au moment de créer le pod, pas avant.
- Un PVC déjà `Bound` **le reste** même après suppression du pod qui l'utilisait — le lien PVC↔PV ne se défait pas avec le pod. Pour rejouer un scénario de binding depuis zéro, il faut supprimer explicitement le PVC (et le PV si `reclaimPolicy: Retain`).
- `hostPath` : jamais en production (accès direct au système de fichiers du nœud = faille de sécurité majeure).

## ✅ À retenir
Toujours vérifier `kubectl get pv,pvc` **avant** et **après** avoir créé le pod consommateur, pour bien observer la transition `Pending` → `Bound` et comprendre à quel moment exact elle se produit.
