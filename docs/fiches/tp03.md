# Fiche TP3 — Persistance des données

## Concepts clés
- **emptyDir** : disque créé vide au démarrage du Pod, partagé entre ses conteneurs, détruit avec le Pod — ni persistant ni partagé entre Pods.
- **hostPath** : monte un chemin du système de fichiers du **nœud** dans le Pod — jamais en production (accès direct au filesystem hôte = faille de sécurité majeure, et le Pod redémarré sur un autre nœud ne retrouve pas ses données).
- **PersistentVolume (PV)** : la ressource de stockage réelle (disque réseau, NFS, ou hostPath pour du dev), créée par un administrateur ou dynamiquement. **PersistentVolumeClaim (PVC)** : la demande d'un utilisateur/pod ("je veux 1Gi en ReadWriteOnce"), que Kubernetes fait correspondre à un PV compatible.
- **StorageClass** : décrit comment provisionner un volume (`provisioner: kubernetes.io/no-provisioner` pour du manuel, ou un vrai provisioner cloud pour du dynamique) et surtout son `volumeBindingMode`.
- `accessModes` : `ReadWriteOnce` (un seul nœud à la fois, le plus courant), `ReadOnlyMany`, `ReadWriteMany`. `reclaimPolicy` : `Delete` (le PV disparaît avec le PVC) ou `Retain` (le PV et ses données survivent, à nettoyer manuellement).

## Commandes essentielles, expliquées

```bash
kubectl apply -f 02-storage-class-manual.yaml
```
Crée l'objet StorageClass. À lui seul, il ne crée aucun stockage : c'est une règle que les PV et PVC référencent ensuite par leur `storageClassName` pour se trouver mutuellement.

```bash
minikube ssh "sudo mkdir -p /mnt/data"
```
Crée le répertoire sur le **nœud** minikube lui-même (une petite VM/conteneur), pas sur la machine hôte qui lance minikube. Nécessaire avant de créer un PV `hostPath` pointant vers ce chemin, sinon le montage échoue silencieusement (répertoire vide créé à la volée, ou erreur selon le `type` du hostPath).

```bash
kubectl apply -f 03-persistent-volume.yaml
kubectl get pv
```
Crée le PV. Son statut passe à `Available` dès sa création — ce n'est encore lié à aucun PVC.

```bash
kubectl apply -f 04-persistent-volume-claim.yaml
kubectl get pvc
```
Crée le PVC. Kubernetes cherche un PV compatible (même `storageClassName`, `accessModes` inclus dans ceux du PV, capacité suffisante). **Si la StorageClass utilise `volumeBindingMode: WaitForFirstConsumer`, le PVC reste `Pending` ici, volontairement** — voir le piège ci-dessous, c'est le point le plus important de tout ce TP.

```bash
kubectl apply -f 05-pod-with-pvc.yaml
kubectl get pvc
```
Le Pod référence le PVC dans `spec.volumes[].persistentVolumeClaim.claimName`. C'est au moment où le **scheduler** doit décider sur quel nœud placer ce Pod que le binding PVC↔PV a réellement lieu (avec `WaitForFirstConsumer`) : le PVC passe alors à `Bound`.

```bash
kubectl describe pvc <nom>
```
Affiche les `Events` du PVC — c'est là qu'apparaît une erreur explicite comme `storageclass.storage.k8s.io "manual" not found` si la StorageClass référencée n'existe pas, plutôt que de deviner depuis un simple statut `Pending`.

## ⚠️ Pièges fréquents (les plus importants du dépôt)
- **`volumeBindingMode: WaitForFirstConsumer`** : le PVC reste `Pending` tant qu'aucun **pod** ne le consomme — ce n'est **pas un bug**, c'est voulu : ça permet au binding d'attendre de savoir sur quel nœud le pod sera planifié avant de choisir/lier un volume (essentiel pour du stockage local à un nœud). Le binding a lieu au moment de créer le pod, jamais avant.
- Un PVC déjà `Bound` **le reste** même après suppression du pod qui l'utilisait — le lien PVC↔PV ne se défait pas avec le pod. Pour rejouer tout le scénario de binding depuis un état vierge, il faut supprimer explicitement le PVC (et le PV si `reclaimPolicy: Retain`) : `kubectl delete pod ...`, `kubectl delete pvc ...`, `kubectl delete pv ...`, dans cet ordre.
- `hostPath` : jamais en production, même "juste pour tester vite" — c'est justement ce réflexe qui le fait finir en prod.

## ✅ À retenir
Toujours vérifier `kubectl get pv,pvc` **avant** et **après** avoir créé le pod consommateur, pour observer concrètement le moment exact où `Pending`/`Available` deviennent `Bound` — c'est le meilleur moyen de faire coller le modèle mental à la réalité du comportement du scheduler.
